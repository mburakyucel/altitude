# I-019 — Fix request prescribed a lock that would have deadlocked altd; caught only at review, cost a second build round and the last launch

- date: 2026-08-30
- task: incident-ids-must-be-unique-under-concur
- project: altitude
- what happened: The L3 request for the I-013 fix said allocate "under the project lock (the one every alt transition already takes)" and the brief copied it verbatim. new_incident is reached from inside dispatch.run while it holds S.project_lock (the quota-unknown fault) and flock is not reentrant, so round 1 of the L1 implemented a deadlock of altd. The reviewer caught it as blocker F1; the repair took a second L1 round plus a delta re-review, which spent the third and last launch of the S envelope.
- evidence: tasks/incident-ids-must-be-unique-under-concur/request.md deliverable 1 ("under the project lock"); report.md Review F1 (blocker, fixed) and Deviations 1; spend 34/40 turns, launches 3/3 (implementer, reviewer, delta re-reviewer); PR #37 merged 61a6b7b with a leaf lock incidents/.alloc.lock and test_filing_an_incident_under_the_project_lock_does_not_deadlock (SIGALRM watchdog)
- root cause: The L3 prescribed a concrete locking mechanism in the request without checking the call sites where that lock is already held, and the L2 adopted the prescription without that check. A request should state the invariant and the evidence and mark any mechanism as a suggestion the L2 verifies against every path that reaches the new code.
- generalizable: yes: any fix request that names a lock, an ordering or a shared resource can carry the same latent conflict; the reviewer is the only net
