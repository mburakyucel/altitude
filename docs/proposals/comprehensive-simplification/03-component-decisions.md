# Component decision register

## Purpose and decision rule

This register classifies the entire current Altitude surface against the intended architecture, not
against age, line count, or aesthetic preference. The mechanism to preserve is the small operating
model in which L3 uses judgment, one L2 owns one isolated task, optional L1/reviewer work remains
bounded, changes cross a mechanical PR boundary, provider capacity routes independently, and a
system fault activates a fail-closed recovery fuse. Those invariants are stated in the
[architecture](../../../docs/ARCHITECTURE.md#L1-L22) and the
[current operating model](../../../README.md#L8-L25).

The labels mean:

- **KEEP** — the component and its present responsibility directly implement a desired mechanism.
- **SIMPLIFY** — keep the responsibility, but reduce branches, compatibility behavior, or incidental
  presentation within the component.
- **CONSOLIDATE** — two or more components or artifact families implement one concern; establish one
  canonical owner and make the others adapters or derived views.
- **REMOVE** — the behavior has no desired architectural responsibility, duplicates a stronger
  mechanism, or contradicts the operating model.
- **DEFER** — removal or redesign depends on evidence, a migration, or a product decision that this
  proposal cannot safely assume.

“REMOVE” never means deleting historical runtime evidence. It means stop producing or exposing the
surface after any required migration and retention decision. Tests for a removed behavior retire in
the same change as the behavior, never before it.

## Target and migration component budget

These are proposed responsibilities, not instructions to create one module per row. Their purpose is
to account for new machinery so the refactor cannot appear smaller only by omitting its replacements
from this register.

| Target responsibility/artifact | Lifetime | Replaces or justifies | Deletion/size constraint |
|---|---|---|---|
| In-process application commands | **PERMANENT** | Direct durable writes in server, CLI, Claude commands, and brokers | One authority called by every adapter; it must delete migrated direct writers rather than wrap them indefinitely |
| Typed operation-journal utility | **PERMANENT, deliberately closed** | Dispatch timestamps, L3/action ad hoc journals, completion flags, recovery task-claim/clearance races | Only five variants named in 02; recovery has two fixed subtypes; no DSL, arbitrary callbacks, or plugin registry |
| `TaskRecord` + current `OwnerGeneration` | **PERMANENT** | Overloaded `status.json` identity/state and repeated tuple checks | Product state plus references only; each physical start creates a new fenced generation |
| `worker_transition` journal | **PERMANENT while an operation is live; compact after receipt** | Unrecoverable spawn/bind/stop/steer gaps and dispatch timestamp lease | Deterministic process-unit target and fixed stages only; terminal detail moves to audit events/worker receipt |
| Strict untrusted `WorkerOutcome` | **PERMANENT** | Parallel Claude report and Codex action shapes | Contains no trusted GitHub, verification, or deployment facts |
| `SettlementJournal` | **PERMANENT while settling; immutable compact receipt afterward** | `reported`, verification flag, completion request, stranded closeout, duplicate land retry, merged receipt omitted from deployment | Fixed publication/deployment-contribution/no-code/helper/attention stages; deterministic contribution key; no general workflow authoring |
| Publication/Verification/NoCode receipts | **PERMANENT audit evidence** | Rediscovered PR lists/check verdicts and model-authored completion truth | One receipt per actual attempt/effect; read models select the current/final reference |
| `operational-holds.json` | **PERMANENT active control state** | Provider/project/task operational holds and their UI mirrors | Only non-global holds; cleared entries move to audit history instead of accumulating active state |
| `recovery.json` + clearance ledger | **PERMANENT safety core** | v1 recovery hold/attention/derived project holds | Active episode only; absent after clearance; no empty generation or central extensible rules engine |
| `DeploymentRecord` + activation receipts | **PERMANENT** | `restart-pending`, task-local deployment flags, scheduler self-deploy | One per deployable service; idempotent receipt contributions; many merges map to one activated SHA by ancestry; activation uses its own fixed closed operation |
| Helper records | **PERMANENT only while D3 retains managed helpers** | L1 PR aggregation and scattered helper artifacts | Prompt, parent fence, process, patch/findings, terminal receipt only; never PR ownership |
| Typed read models | **PERMANENT** | Duplicate server/status/monitor/UI projections | Read-only; no persisted mirror is allowed to actuate behavior |

## Required sequencing and stop conditions

The classification is not an instruction to delete in place. Safe reduction follows dependency
order:

1. Define canonical typed **WorkerOutcome**, **Publication scope**, **Task/Operational projection**, **Provider quota
   observation**, and **application command** contracts.
2. Add backward readers or one-time migrations for active/resumable task records, L3 sessions,
   pending action journals, incident indexes, and historical transcript bundles.
3. Move every producer and consumer to the canonical contract, with characterization tests still
   protecting containment, recovery, Git publication, and stale-worker fencing.
4. Remove contradictory/dead product surfaces: direct Project task creation, manual web Dispatch,
   project approval, digest/TTS, edit telemetry, L1 PR remnants, `report.md` probes, `hold.json`, and
   the dead statusline HTTP endpoint.
5. Split large modules only after behavior is shared; then remove compatibility branches and old
   artifact readers once runtime inventory proves they are no longer needed.

Stop and re-evaluate any simplification that would weaken one of these properties: one current task
owner; task publication-scope authority and L1-only subleases; exact worktree/branch/base provenance; trusted-only Git,
state, and publication actions; independent provider capacity; durable direct conversation;
fail-closed recovery with one repair and explicit clearance; or preserved private audit evidence.
